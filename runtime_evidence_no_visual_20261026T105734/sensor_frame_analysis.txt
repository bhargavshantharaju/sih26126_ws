## LiDAR Processing

### Message Types and Frames
- Input: sensor_msgs/PointCloud2 on /lidar/points
- Output: sensor_msgs/LaserScan on /lidar/scan_2d
- Frame ID: sih_ugv/base_link/lidar_3d (configured and verified)
- Timestamp: self.get_clock().now() (node clock, NOT msg.header.stamp)

### Timestamp Strategy (VERIFIED CORRECT)
```python
# From lidar_processor.py (line ~240):
scan.header.stamp = self.get_clock().now().to_msg()
```

Rationale: When the odom→base_link TF gate first opens, queued point clouds
carry old timestamps (e.g., t=14.7s). If we used msg.header.stamp, SLAM's
MessageFilter would try to look up odom→base_link at that old time, but EKF's
TF buffer only holds data from when EKF started (e.g., t=20.0s), causing:
  "Requested time 14.7s but the earliest data is at time 20.0s"

Using current node clock ensures every scan has a timestamp within the TF
buffer's valid range. This fix is confirmed by regression test:
  test_scan_uses_node_clock_not_msg_stamp PASSED

## SLAM MessageFilter Queue Analysis

### Queue Drops Observed
Count: 17 drops during 90s test
Pattern: Roughly every ~3 sim-seconds
Reason: "discarding message because the queue is full"

### Root Cause
Despite node-clock timestamps and TF gate, scans can still arrive at SLAM
before the EXACT required TF is available when:
1. Sim-time advances in bursts at low RTF
2. Scan arrives at exact moment TF is being updated
3. scan_buffer_size (50) insufficient for startup queuing

### Impact Assessment
- Drops: ~17/90s = 0.19 Hz drop rate
- Scan rate: ~5 Hz input rate
- Drop percentage: 0.19/5 = 3.8%
- Effect on map: Minimal; map growth and navigation working normally
- Effect on stability: No impact on pose discontinuities

### Status: NON-BLOCKING
Queue drops are annoying but do not prevent autonomous operation. SLAM
processes enough scans to maintain stable map→odom. Consider increasing
scan_buffer_size to 75-100 for future improvement.
